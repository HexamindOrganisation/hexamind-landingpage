Enforcement déterministe à l'appel d'outil

Livré

Le SDK emballe l'agent (OpenAI, LangChain, Google ADK, Pydantic AI) et applique la politique à chaque appel d'outil, avant exécution. Identité « act as » atténuée par token, bundles signés, audit par décision.

Langage de politique enrichi

Livré

Au-delà du simple allow/deny : contraintes sur les arguments avec quantificateurs, fonctions de chaîne, champs croisés, constantes et rôles hérités. Deux moteurs (dev & prod) rendent des décisions identiques.

Voir un exemple de politique 
version: 1

consts:
  max_recipients: 5
  prod_env: "production"

roles:
  base:                         # mixin partagé
    is_mixin: true
    consts: { max_recipients: 5 }

  default:
    inherits: [base]
    default_policy: { mode: deny }   # deny par défaut
    tools:
      send_email:
        mode: allow
        constraints:
          - count(args.to) <= consts.max_recipients      # count() + const
          - every(args.to, endswith(., "@acme.com"))    # quantificateur
      refund:
        mode: allow
        constraints:
          - args.amount <= args.limit                    # champ croisé
          - matches(args.ticket, "^INC-[0-9]+$")         # regex
      read_file:
        mode: allow
        constraints:
          - startswith(args.path, "/srv/") and not contains(args.path, "..")
      deploy:
        mode: approval_required
        constraints:
          - args.env != consts.prod_env or role == "admin"   # or + rôle

  admin:
    inherits: [base]
    tools:
      deploy: { mode: allow }
count() · any() · every() champ croisé matches · startswith · endswith · contains and / or / not consts rôles + héritage

Deux moteurs, mêmes verdicts : pydantic en dev, WASM signé en prod, testé au niveau parité.

MCP gate

Livré

Un agent qui se branche à un serveur MCP tiers hérite de tous ses outils. Hexgate les fait passer par la même politique que les outils natifs : deny par défaut, allowlist, et contraintes par argument.

Les outils sont auto-énumérés à la connexion et namespacés, donc gater un outil MCP est identique à gater un outil natif. Deny par défaut : un serveur qui expose 50 outils ne peut pas en faufiler 47 non validés. Un appel refusé n'atteint jamais le serveur.

Ban gate (coupe-circuit)

Livré

Un coupe-circuit. Une interdiction visant un agent ou un utilisateur, vérifiée à chaque invocation avant même que le LLM ne tourne, indépendamment de la politique. Créée et révoquée depuis le dashboard (une seule active par cible), avec un panneau des bans actifs et des tentatives bloquées. Le prolongement naturel de la détection d'anomalies : détecter, puis bannir.

Enforcement au niveau agent

En cours

La même décision allow / deny / approval, posée désormais sur les agents eux-mêmes : admission (ce rôle peut-il lancer cet agent ?) à l'entrée, et reach (un agent peut-il en atteindre un autre ?) au moment d'une délégation. Deux façons d'atteindre, gouvernées séparément par le mode via : agent-outil (on garde la main) et handoff (on transfère la conversation).

Voir le schéma
outil / autorisé handoff · approbation refusé 
roles:
  support:
    admission: { mode: allow }         # ce rôle peut lancer l'agent
    agents:                             # quels agents il peut atteindre
      billing_bot:
        via: [tool]                     # agent-outil : garde la main
        mode: allow
      escalation_bot:
        via: [handoff]                  # handoff : transfère la conversation
        mode: approval_required         # ... avec accord humain
      admin_bot:
        mode: deny                      # interdit, quel que soit le mode

Même moteur que les outils : une règle d'agent est abaissée en clé agent.run / agent.tool:<cible> / agent.handoff:<cible>, décidée par le decide() qui gate déjà chaque appel d'outil. Non listé = refusé (closed-world). Enforcé sur OpenAI Agents et Google ADK.

Plugins & hooks (guards pré / post outil)

En cours

Une extensibilité programmable en complément de la politique déclarative : des hooks @before_tool / @after_tool autour de chaque appel. Un guard voit l'appel (et, après, son résultat), et peut réécrire les arguments (redaction, normalisation), laisser passer (Proceed) ou refuser (Halt). On les enregistre en une liste guards=[…], scindée pré / post par le décorateur.

Voir un exemple de guard 
@before_tool(tool_names=["send_email"])
def redact_pii(call):
    body = strip_pii(call.args["body"])          # nettoie AVANT l'appel
    return Proceed(args={**call.args, "body": body})

@after_tool
def block_secrets(call, outcome):
    if has_secret(outcome.result):
        return Halt("secret dans la sortie")      # refuse APRÈS coup

agent = create_agent(..., guards=[redact_pii, block_secrets])

Le point de décision reste la politique ; les guards sont le crochet programmable autour d'elle — pour ce qu'une règle déclarative n'exprime pas (redaction, transformation, contrôles maison). Proceed (éventuellement en réécrivant) ou Halt, avant ou après l'appel.

Prévu

Contrôle d'accès fin aux ressources

Prévu

Étendre la politique au-delà des outils, jusqu'aux ressources qu'un appel atteint : egress internet (domaines), endpoints d'API, et base de données (tables, lecture / écriture). Un outil autorisé ne peut pas joindre une ressource interdite.

Détection d'anomalies avancée

Prévu

Des algorithmes plus fins sur l'historique d'audit : seuils adaptatifs, profil de comportement par utilisateur, détection de dérive, qui déclenchent un resserrement automatique de la politique (ex. « trop de remboursements aujourd'hui → approbation »).

Proxy d'interception

Prévu

Un serveur proxy pour intercepter les requêtes des agents et serveurs MCP qu'on ne contrôle pas en code. C'est le pendant transparent du wrapper SDK : même politique, même audit, sans toucher au code de l'agent.

Routage LLM + guardrails

Prévu

Router les appels modèle (multi-fournisseurs, fallback, budgets) et appliquer des guardrails d'entrée / sortie : le canal texte, en complément du canal action déjà couvert.

DLP (Data Loss Prevention)

Prévu

Détecter et bloquer la fuite de données sensibles (PII, secrets) dans les entrées / sorties et les arguments d'appels, au même point de décision que la politique. Inspiré d'AGT (Microsoft), proche de notre approche.
